## U-01 — The map draws itself outside the token system · High · OBSERVED

`ui/src/core/components/MapCanvas.vue`:

```css
.pin__puck {
  color: #fff;
  background: var(--pin-color);
  border: 2px solid #fff;
  box-shadow: 0 1px 4px rgba(0, 0, 0, 0.35);
}
.pin--stale .pin__puck { background: #fff; color: var(--pin-color); }
.cluster {
  background: var(--pin-color);
  color: #fff;
  border: 2px solid #fff;
  box-shadow: 0 1px 4px rgba(0, 0, 0, 0.35);
}
```

Six hardcoded colour literals in the surface a driver opens more than any other. Everything around
them is tokenised — `var(--pin-color)`, `var(--text-3)`, `var(--type-caption-size)` — so this is an
island, not a house style.

**Why it is more than a style violation.** These literals are **theme-invariant**. `--pin-color`
changes between dark and light themes; `#fff` does not. In dark theme a white ring around a coloured
puck reads correctly. In light theme the same white ring sits on a light map background and the pin
loses its outline — and `.pin--stale` inverts to a **white puck with a white border**, which is the
stale-pin affordance §11.7 relies on to say "this reading is old."

The project has been here before: §23 entry 45's light-theme close-out argued the theme was safe
because *"contrast is verified from tokens in CI across both themes."* That argument holds only for
values that are tokens. These six are the exception it did not cover, and the CI contrast check
cannot see them.

**Also worth noting:** the same file is where `.pin` correctly carries `width: 44px` with the comment
`/* §11.2: 44 dp hit area */`. The author was reading the constitution while writing this file. The
colours were simply not part of what got checked.

**Fix:** two tokens — a pin foreground and a pin elevation shadow — defined per theme. `rgba(0,0,0,
0.4)` at `12-ui-core.md:1828` (a scrim) is the third literal and belongs in the same change.

## U-02 — A new driver inherits the last one's active stop · High · OBSERVED

```js
export function logout() {
  token.value = null;
  account.value = null;
  email.value = null;
  persist();
  clearCache();   // "a new driver never sees the last one's cached reads"
  saveQueue([]);  // "...nor inherits their unsynced writes"
}
```

`clearCache()` removes keys prefixed `longhaul.cache.`. Two keys are **not** prefixed and survive
logout:

| Key | Holds |
|---|---|
| `longhaul.active_stop` | the previous driver's active stop id |
| `longhaul.active_fleet` | the previous driver's fleet id |

The comments on those two lines state the intent precisely — and the implementation misses it by a
naming convention. This is the same shape as the backend's F-11: a rule enforced by prefix, and two
members that never got the prefix.

**Why it matters in this product specifically.** A phone handed between team drivers, or a cab
tablet, is the normal case, not the edge case. The active stop is what the Load tab, The Meter and
the arrival prompt anchor to. Driver B signs in and the client asks the server about driver A's stop.

The server should refuse — ownership checks looked sound in the backend sweep — so the likely
outcome is a broken screen rather than a data leak. But "the API happens to 404" is not the guard the
comment claims to be, and a Meter anchored to a stop that is not yours is exactly the class of
confusion this product cannot afford on a screen that decides money.

**Fix:** clear both keys in `logout()`, or bring them under `CACHE_PREFIX`. The second is better —
it makes the convention self-enforcing.

## U-03 — English reaches drivers, and nothing detects it · High · OBSERVED

PRD v2.0 §8, acceptance criterion 5: *"Six locales complete for every new string; **no English
fallback reaches a driver**."*

```js
function resolve(key, catalog) {
  if (Object.hasOwn(catalog, key)) return catalog[key];
  const fallback = messages[DEFAULT_LOCALE];
  if (Object.hasOwn(fallback, key)) return fallback[key];   // <-- English, silently, in production
  if (UNDER_TEST) throw new Error(`i18n: no string for "${key}" in any locale...`);
  return key;
}
```

The guard fires only when a key is missing from **every** locale. A key present in English and
missing in Somali returns **English text to a Somali driver**, with no error, no warning, and no
visible difference from a correct translation.

That is the exact condition acceptance #5 forbids, and the resolver implements it as the designed
fallback path.

**The blind spot is documented in the file itself:**

> a list rots, and there are ~45 dynamic `t(\`ns.${...}\`)` families whose vocabularies live in
> Python. The static half is checked directly in `locale-completeness.test.js`.

So the static keys are covered by CI. The ~45 dynamic families — where the key is assembled at
runtime from a Python-side vocabulary — cannot be enumerated by a JS test, are not caught by the
resolver, and are not visible in the layout harness (which renders one locale at a time against
mocks). Five of six locales can be English for those strings and nothing in the pipeline says so.

**This is not a hypothetical.** The dynamic families are where server-driven vocabularies live —
facility kinds, service types, claim states, notification categories. Those are precisely the strings
a non-English driver meets on the Map and Money tabs.

**Fix shape:** make the fallback loud rather than silent. A dev-mode `console.warn` on every
cross-locale fallback, plus a runtime counter surfaced in the dev index, converts an invisible gap
into a measurable one — which is the only way a list that rots can be kept honest. The stronger
version is to generate the dynamic key list from the Python enums at build time, so the JS test can
check it.

## U-04 — Seven surfaces are not in the layout harness · Medium · ABSENT

PRD v2.0 §8, acceptance criterion 3: *"Every new surface registered in the layout harness **in the
same commit** that creates it."*

The harness `SURFACES` array covers roughly 60 states. Cross-referencing against the 21 files in
`ui/src/surfaces/`, these have no entry:

| Surface | Route | Notes |
|---|---|---|
| **ClaimSurface** | `/claim/{stop_ref}` | **the deep-link target for every detention notification** (§13.5, `_receivable_deep_link`) |
| AuditSurface | `/money/audit` | M9 settlement audit |
| FuelSurface | — | M7, driver-facing |
| BookingSurface | — | M6, driver-facing |
| FleetWorkspaceSurface | `/fleet` | portal |
| OwnerPortalSurface | `/owner` | portal |
| PublicScorecardSurface | `/scorecard` | public |

(`DevIndexSurface` and `PlaceholderSurface` are correctly excluded — a dev tool and a stub.)

**ClaimSurface is the one that matters.** §13.5 forbids a notification deep-linking to a tab root and
requires the exact claim; the backend enforces this (`dispatch` refuses without a deep link). So
every detention alert a driver receives lands on a screen that **has never been measured at 360 × 800
under +40% type in six locales** — while the surfaces they navigate to themselves have been, some in
four separate states.

The three portals are arguably lower priority: design-prd §18 makes them web-first. But it also says
mobile-usable, and LAW 0 has no portal exemption written into it.

**Correction to my own method.** My first extraction of `SURFACES` read only the opening lines of the
array and reported eleven entries, which would have made this finding four times larger than it is.
The array runs ~340 lines and is genuinely thorough — including twenty-plus bottom-sheet states, each
with a `ready` selector proving the mocked state actually rendered. Recorded because a false alarm
about test coverage is worth being explicit about.

## U-05 — Targets below the glove floor · Medium · OBSERVED

design-prd §6.5: *"Minimum target **48 × 48 dp**."* The rationale is stated in §6: a gloved hand, in
a bouncing cab, in glare.

| Element | Height | File |
|---|---|---|
| `.filters-chip` | `min-height: 40px` | `MapSurface.vue` |
| (fleet control) | `min-height: 40px` | `FleetWorkspaceSurface.vue` |
| `.spot__price-in` | `min-height: 40px` | `OwnerPortalSurface.vue` |
| `.cluster` | `36px` | `MapCanvas.vue` |

**Three of these are defensible and one is not.**

`.cluster` is a map cluster chip, and §11.2 sets pin hit areas at 44 dp explicitly — a documented
carve-out from the 48 dp floor, and `.pin` honours it. Whether 36 dp clears even that is worth a
measurement, but it is a different question from a violation.

The two portal controls sit on web-first surfaces where the glove rationale does not apply, though
nothing in §6.5 grants that exemption in writing.

**`.filters-chip` in `MapSurface.vue` is the real one.** It is a driver-facing control, on the
daily-open surface, at 40 dp — 8 dp under the floor, on the screen §6 was written about. Its own
comment says *"the same pill the preset row uses — no new component pattern (§22.2)"*, which suggests
the preset row may also be 40 dp; if so, the violation is the shared pattern rather than this one
chip, and fixing it fixes both.

**Worth checking whether the layout harness asserts a minimum target size at all.** If it measures
overflow and contrast but not hit area, then §6.5 has no automated enforcement anywhere — which
would explain how a 40 dp control reached the map surface.

## What is clean

### 5.1 LAW 0 is honoured absolutely
**Zero** `max-width` media queries across `ui/src/core`, `ui/src/surfaces` and the rest of `ui/`.
Six `min-width` queries, all in surfaces. For a codebase this size that is a perfect result on the
law most likely to erode, and it means the mobile-first baseline is structural rather than
aspirational.

### 5.2 No XSS surface
**Zero** occurrences of `v-html` anywhere in the UI. Every driver-visible string goes through Vue's
escaped interpolation or `t()`. Given that vendor names, promotion text and review bodies are
user-supplied and reach the Map and facility cards, this is the single most valuable absence in the
codebase.

### 5.3 The service-worker token mirror is cleared correctly
`watch(token, mirrorTokenToIdb, { immediate: true, flush: "sync" })` — so the IndexedDB copy the
service worker reads is deleted the moment `token.value` becomes null, in the same tick. I went
looking for a logout gap here and there is not one; the reactive wiring makes it correct by
construction rather than by remembering to call it. (U-02's gap is elsewhere and is not this.)

### 5.4 The layout harness is serious work
~60 registered states, not 21 — bottom sheets, prefilled versus empty forms, deep-link landings, a
marked-document state, service-facility variants with and without contact. Nearly every entry carries
a `ready` selector, and the AI-CONTEXT explains why: *"without it a mock that stops matching turns
this surface back into a second copy of `load`, and the harness goes green over the screen it was
added to measure — the same failure as the run that measured Vite's error page six times."* That is a
harness written by someone who has been burned by a green harness and fixed the cause.

### 5.5 i18n throws under test for wholly-missing keys
`resolve()` raises in test mode with a message naming the law (*"A driver would read the raw key —
design-prd §12.5 / Forbidden #7"*) and the required action. The failure it cannot see is U-03; the
one it can see, it fails loudly and instructively.

## U-06 — Money the driver has not earned, on the Money tab · **Critical** · OBSERVED

Two surfaces substitute **fixtures** when a fetch fails.

`MoneySurface.vue`:

```js
const rows = ref(SAMPLE_OWED);
const earnings = ref(SAMPLE_EARNINGS);

onMounted(async () => {
  try { rows.value = await fetchOwed(); }
  catch { rows.value = SAMPLE_OWED; }          // unauthenticated / offline
  try { earnings.value = await fetchEarnings(); }
  catch { earnings.value = SAMPLE_EARNINGS; }  // unauthenticated / offline
});
```

`AuditSurface.vue`:

```js
catch {
  result.value = sampleAudit();   // unauthenticated / offline
}
```

What those fixtures contain:

```js
SAMPLE_EARNINGS = { recovered_cents: 12500, fuel_saved_cents: 36250,
                    flagged_cents: 10000, ddd_cents: 58750 }

sampleAudit()  = { discrepancies: [{ kind: "detention", owed_cents: 15000,
                     paid_cents: 5000, missed_cents: 10000, status: "flagged" }],
                   total_missed_cents: 10000 }
```

So a driver in a dead zone opens **Money** and reads *$587.50 Driver Dollars Delivered* — the
product's own North Star figure — of which none is theirs. They open **Money → Audit**, fill in their
settlement, tap the button, and are told *the broker missed $100 on your detention*. There is no
pill, no caption, no marking of any kind in either template.

**Three things make this worse than an ordinary fixture leak.**

**It is the exact defect §23 entry 52 already fixed, one tab over.** That entry removed a fixture load
from the Load tab and its AI-CONTEXT reads: *"the loudest thing on a screen with no load was money
the driver had not earned."* The same sentence describes this, and the fix did not travel. This is the
UI instance of the backend's propagation pattern (F-21).

**On Audit it is not an empty state — it is a result.** The Load tab's fixture appeared before the
driver did anything. Here the driver enters their settlement figures, taps a button, and receives a
number back. Every cue says *this is your answer*. Nothing distinguishes it from a real one.

**`ddd_cents` is the North Star.** PRD v1.0 makes Driver Dollars Delivered the measure the whole
product is judged by. Rendering a fabricated value for it, unmarked, on the tab named Money, is the
§11.7 failure in its most expensive location.

**The `catch` is also too broad.** It cannot distinguish offline from a 401 or a 500, so a signed-in
driver whose session expired on a good connection gets the same invented figures.

**Fix:** delete the fallbacks. §15.3 already specifies what belongs there — *"Empty Money: 'Recovered
and saved money shows up here. Add your first load to start the meter.'"* — and §15.4 requires errors
to be inline, specific and actionable. An offline Money tab should say it is offline. It should never
say a number.

## U-07 — A rejected offline write disappears without trace · **Critical** · OBSERVED

`core/api.js`:

```js
export async function flushQueue() {
  ...
  const q = readQueue();
  while (q.length) {
    const item = q[0];
    try {
      await fetch(`${API_BASE}${item.path}`, { ... });   // resp.ok is NEVER checked
    } catch {
      online.value = false;
      break;
    }
    online.value = true;
    q.shift();          // "drop on success OR server-rejection"
    saveQueue(q);
  }
}
```

The comment states the intent plainly: *"drop on success OR server-rejection (don't retry a bad write
forever)."* The instinct is right and the implementation loses the write.

`resp.ok` is never consulted, so a 400, 401, 403, 409, 422 or 500 is **indistinguishable from a
success**. The item is shifted off the queue, `saveQueue` decrements `pendingWrites`, and the status
strip — the only surface that ever reports sync state — returns to zero. The driver is shown *synced*.

**The concrete case this product exists to serve.** A driver photographs a BOL at a dock with no
signal. It queues. Two hours later the phone reconnects, the replay fires, the server returns 401
because the session expired overnight. The evidence is dropped. The driver believes it is filed. It
is not in the evidence chain, and nothing anywhere records that it was lost — not a log, not a
counter, not a badge.

That evidence is what a detention claim is made of. §15.4 is explicit: *"Failed money-moving actions
are always explicit and persistent until resolved."* This is the opposite — silent and permanent.

It is also §11.7's absence-dressed-as-a-result, in the same shape as the backend's F-01 (an F8 row
saying a notice was sent) and the merged-facility crowd report (§23) that told a driver their
submission landed when nothing would ever see it. **Three instances of one pattern, in three layers.**

**Fix shape:** a dead-letter, not a drop. Check `resp.ok`; on a permanent rejection move the item to
a `longhaul.failed_writes` list and surface it — the status strip already renders a pending count and
can render a failed one. The driver does not need to understand a 422; they need to know that one
thing did not go, and which one.

## U-08 — A transient failure is treated as permanent · High · OBSERVED

Same block. Because `resp.ok` is unchecked, a **500** — the server is briefly unwell, the write is
perfectly valid — is handled identically to a **422** — the write is malformed and will never
succeed. Both are shifted off the queue and lost.

The distinction is the one that decides whether a retry is useful:

| Status | Retry? | Current behaviour |
|---|---|---|
| network throw | yes, later | correct — `break`, keeps the queue |
| 5xx, 429 | **yes, with backoff** | **dropped** |
| 4xx | no — dead-letter it | dropped silently (U-07) |

A deploy, a container restart, or the box being briefly down — all normal for a single VM with no
monitoring (A12) — silently destroys every queued write that happens to replay during the window.

This compounds with the backend audit's F-01: if the deployed box is misconfigured, replays may be
failing right now, and by design nothing would say so.

## What is clean, part 2

### The DRIVING guard is the best-enforced law in the codebase
Every driver route carries `meta.driving`, and `driving-posture.test.js` asserts that the declared set
covers exactly the driver routes — so a new route cannot slip through unguarded. The §23 record shows
this was earned rather than assumed: entry 1198 found *seven of thirteen driver surfaces with no
DRIVING behaviour at all*, including `ConditionSurface` opening a **camera at speed** via a deep link.

Two details worth naming:

- The systemic fix — a global `beforeEach` redirect — was **rejected** because it would break §13.5's
  deep-link law for every notification the product sends. The chosen mechanism is a declaration plus
  a test. That is the harder and correct answer.
- Entry 1197 caught that *"the control that opens a flow and the flow itself are two different things
  to guard"* — a capture chip was `v-if="!isDriving"` while the sheet it opened was a sibling and was
  not. Sheets now **close** rather than hide, so nothing springs back open at the next stop.

**A1's new surface honours it.** `StopPacketsSurface` — the newest route in the tree — carries
`driving: "withdraws"` with a written reason: *"sending a document to a broker is the last decision
that belongs in front of someone at 65 mph, and the packet waits."* `ClaimSurface` is `safe`, which is
right: it is §13.5's deep-link target and must be readable at speed, read-only.

### The offline queue's idempotency is correct
Each queued write carries a stable `opId` generated **once** and re-sent on every replay, so F12's
`(account, idempotency_key)` uniqueness makes a write that reached the server before the dead zone
apply exactly once. This is the pattern the backend's F-05 and F-13 are missing, implemented properly
on the client. U-07 and U-08 are failure-handling defects on top of a correct core.

### Reconnect wiring is complete
`window.addEventListener("online", …)` drains the queue, `navigator.onLine` seeds the initial state,
a flush runs on mount for a previous session's queue, listeners are removed on unmount, and
`_flushing` prevents re-entrancy. No gap found.

## U-09 — Six surfaces substitute invented data on failure · **Critical** · OBSERVED

| Surface | Fallback | What a driver is shown |
|---|---|---|
| `MoneySurface` | `SAMPLE_OWED`, `SAMPLE_EARNINGS` | $587.50 Driver Dollars Delivered (U-06) |
| `AuditSurface` | `sampleAudit()` | "the broker missed $100" (U-06) |
| **`DocsSurface`** | `SAMPLE_WALLET` | **a CDL, a med card, insurance — none theirs** |
| **`MapSurface`** | `SAMPLE_PINS`, `sampleHandoffs()` | **truck stops that do not exist** |
| `FacilityProfileSurface` | `sampleProfile()`, `sampleFacilityIntel()`, `sampleQuestions()` | invented facility intel |
| `FleetWorkspaceSurface` | `SAMPLE_FLEET` | invented fleet figures |

Every one is a bare `catch` that cannot distinguish offline from a 401 or a 500.

### DocsSurface is the one that matters most

```js
try { data.value = await fetchWallet(); }
catch { data.value = SAMPLE_WALLET; }
```

`SAMPLE_WALLET` contains four documents — a CDL expiring 2027-03-01, a med card marked **expiring**,
insurance marked **expired**, and a permit — plus an `expiring` list driving the reminder ladder.

M5's stated purpose is producing a credential at the roadside. The §23 entry that built the document
viewer says it in words this audit cannot improve on:

> an officer asking for a CDL got a row reading "CDL · 2028-01-17", which is not a credential, it is
> our claim that the driver has one. **Asserting on a driver's behalf to a police officer is the
> worst possible version of the honesty problem this product keeps solving elsewhere.**

That entry fixed the *viewer* by serving real bytes. The fallback re-creates the exact failure one
layer up and makes it worse: the row is now **entirely fabricated**. A driver in a dead zone at a
scale house opens Docs and sees a wallet that is not theirs — and a driver who taps through will hit
`view_document`, which correctly 404s a document id that is not theirs, producing a fumble in front
of an officer.

Secondary: the fabricated `expiring` list means an offline driver can be told their med card is
expiring when it is not, or reassured when their real one is.

### MapSurface: a lot that does not exist

```js
catch (e) {
  if (e.name === "AbortError") return;
  livePins.value = null;      // fall back to fixtures
  clusters.value = [];
}
```

`rawPins` then returns `SAMPLE_PINS` filtered by preset, with fabricated parking statuses. A driver
whose overlay fetch fails sees truck stops with availability badges, and can take an exit at 2am for
a lot that is not there.

The irony is on the same screen. Twelve lines above `rawPins`, the author reasons carefully about
honest empty states for the service preset:

> Coverage is nine states and the service rules were starved for the whole life of the project, so a
> driver in most of the country will tap this chip and find nothing. **"None mapped here yet" is a
> true sentence; a blank map is not.**

That is exactly right, and it is undone by the function below it. `serviceEmpty` can never fire while
`rawPins` guarantees pins.

### It is not a leak, it is a designed fallback

Every instance carries the same comment — `// unauthenticated / offline` — so this is intentional
behaviour, presumably to make surfaces demonstrable before auth existed. That intent is obsolete: the
product is live, and `/dev` exists for demonstration.

**Fix:** delete every fallback. §15.3 already specifies what belongs in their place and §15.4 requires
errors to be inline, specific and actionable. "Can't reach the server" is a true sentence; a fixture
is not.

## U-10 — The map shows fixture pins on every cold start · **Critical** · OBSERVED

`livePins` initialises to `null`, and `rawPins` returns `SAMPLE_PINS` whenever it is null. `loadOverlay`
sets it only after the first response resolves.

**So the fixture is not the offline path — it is the default path.** Every time the app opens, the map
renders fabricated truck stops with fabricated statuses until `/map/overlay` returns. On a truck-stop
wifi or a rural cell, that is seconds of a driver looking at a map of places that do not exist, with
no loading state distinguishing it.

**This is already documented as a hazard — in the test suite.** The layout harness carries this
comment:

> `open: [".pin"]` looked fine and failed under load: the surface falls back to SAMPLE_PINS **while
> `/map/overlay` is still in flight**, so the step clicked a FIXTURE pin, opened the wrong card, and
> the `ready` selector timed out. Worse, had the two cards shared a lead rung it would have gone
> green having measured the wrong screen.

The harness was hardened by targeting the mocked facility id. **The behaviour that caused it was left
in the product.** A known-hazardous default was fixed in the test rather than at the cause — which is
the third instance of this project's propagation pattern (F-21 in the backend, U-06 across tabs, this).

**Fix:** `livePins` starting as `null` should render §8's skeleton, not data. The distinction the code
needs is three-state — *loading* / *loaded* / *failed* — and it currently has one.

## The single pattern this audit found

Eight criticals, and six of them are one sentence:

> **The product asserts something it does not know.**

- F-01 — an F8 row says a notice was sent; it may have gone to a bin
- F-21 — M4 files a layover claim for a stop that was never overnight
- U-06 — the Money tab shows money the driver has not earned
- U-07 — the status strip says synced after discarding a write
- U-09 — the wallet shows a CDL that is not theirs
- U-10 — the map shows a truck stop that does not exist

§11.7 is the law all six break, and the project already knows it — every one of these sits beside an
AI-CONTEXT or §23 entry arguing the honesty case correctly for an adjacent case. The gap is never
understanding. It is that a fix lands where it was found and not where the pattern lives.

**The cheapest countermeasure is not a redesign.** It is a rule: when a §23 entry records an honesty
defect, the entry must name **every** call site of the pattern, and the session must grep for them.
Four of these eight would not exist.

## U-11 — There is no loading state · High · ABSENT

design-prd §8: *"**Empty/loading:** skeletons mirror the real layout (**no spinners for content**);
empty states = one line of what this is + one action to start."*

Measured across `ui/src/**`:

- **Zero** skeleton components, classes or utilities. The word does not appear.
- **Two** surfaces track loading at all: `FleetWorkspaceSurface` (`view = ref("loading")`) and
  `StopPacketsSurface` (`loading = ref(true)`, rendering a text line, not a skeleton).
- The remaining **19 surfaces have no loading state whatsoever.**

**This is why the fixtures exist.** A surface with two states — *data* and *no data* — must render
something the moment it mounts, before any fetch resolves. With no third state, `null` has to mean
one of the two, and the codebase chose *data*. U-10 is not a slip; it is the only thing a two-state
surface can do.

```js
const livePins = ref(null);                 // no loading state
const rawPins = computed(() =>
  livePins.value ?? SAMPLE_PINS.filter(...)  // null must mean something. it means fixtures.
);
```

**The sequencing consequence matters more than the finding.** Deleting the fixtures (U-09) without
adding a loading state leaves a blank screen on every cold start — which §8 forbids just as clearly.
**These are one change, not two.**

**And it needs an owner decision first.** A skeleton is a component pattern, and §22.2 makes component
patterns a never-improvise category. There is no existing shape to compose from — this is genuinely
new and needs a §23 entry before anyone writes it. Expect one skeleton primitive that mirrors a card,
a row and a pin cluster; do not expect a session to invent three.

## U-12 — The ban, the test, and the nine fixtures it does not cover · High · OBSERVED

`ui/test/corridor.test.js`:

```js
describe("§23 entry 81 — the corridor is served, not invented", () => {
  it("no longer ships a corridor fixture at all", () => {
    // removed rather than left unused: an exported placeholder is one import away
    // from being back on the screen a driver cannot verify
    expect(fixtures.SAMPLE_CORRIDOR).toBeUndefined();
    expect(read("src/core/fixtures.js")).not.toMatch(/^export const SAMPLE_CORRIDOR/m);
  });

  it("wires the surface to the endpoint that was never called", () => {
    const src = read("src/surfaces/MapSurface.vue");
    expect(src).toMatch(/fetchCorridor/);
    expect(src).not.toMatch(/SAMPLE_CORRIDOR/);
  });
});
```

Everything needed is already here — the diagnosis, the remedy (**delete**, do not leave unused), the
reasoning (*"one import away from being back on the screen a driver cannot verify"*), and a structural
test that prevents recurrence.

It covers **one** fixture. `src/core/fixtures.js` still exports at least nine others —
`SAMPLE_PINS`, `SAMPLE_WALLET`, `SAMPLE_OWED`, `SAMPLE_EARNINGS`, `SAMPLE_FLEET`, `sampleAudit`,
`sampleProfile`, `sampleFacilityIntel`, `sampleQuestions`, `sampleHandoffs` — imported by five
surfaces, **including the same `MapSurface.vue` this test guards.** The file the test reads for one
symbol contains nine more it does not look for.

This is the propagation pattern at its purest: same defect class, same file, same surface, same
session's reasoning, one instance fixed.

**It also makes the fix cheap.** The precedent is written and approved; extending the assertion is
close to mechanical:

```js
it("ships no driver-facing fixture at all", () => {
  const src = read("src/core/fixtures.js");
  expect(src).not.toMatch(/^export (const|function) (SAMPLE_|sample[A-Z])/m);
});
```

Green when the last one is gone, red the moment one returns. That test can be written **before** the
fixtures are removed and used as the burn-down.

**One carve-out to decide deliberately:** `/dev` legitimately needs demonstrable surfaces. If any
fixture survives, it belongs behind the dev index and must be unreachable from a driver route — a
distinction the assertion above can encode by path rather than by name.

## What is clean, part 4

### The test suite is not the weak link
The backend audit's recurring pattern — tests asserting the mechanism rather than the outcome — does
**not** reproduce here. The UI tests repeatedly assert the *absence* a driver would experience:

- `corridor.test.js` asserts a fixture is gone from the **file**, not merely unused
- `driving-posture.test.js` asserts the declared route set covers exactly the driver routes, so a new
  route cannot slip through unguarded
- `locale-completeness.test.js` checks catalogues rather than trusting the resolver
- the layout harness carries `ready` selectors *"without those, a mock that drifted would fall back
  to SAMPLE_PINS, open a fixture's card and go green having measured the wrong screen"*

That last comment is a test author who found the fixture hazard, understood it exactly, and hardened
the harness against it. The judgement was right. It stopped at the harness.

### 35 test files, and the naming carries intent
`driving-posture`, `portal-boundary`, `locale-completeness`, `pseudo-locale`, `contrast`,
`typography`, `prompt-controls`, `saved-for-stop` — these are named after **laws**, not after
components. A suite organised by the constitution it enforces is one a reviewer can check against the
constitution.
